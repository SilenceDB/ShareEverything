# ShareEverything

把服务器磁盘上的文件发布出来，通过 Web 分享给局域网 / 其他电脑，带用户鉴权。

- 后端：**Fastify + TypeScript + Prisma + SQLite**
- 前端：**Vue3 + Vite + Pinia + Element Plus**
- 已实现：注册登录（JWT）、**分片上传 + 断点续传 + 秒传**、**可续传下载**、文件上传与目录管理、**本机磁盘资源发布（逻辑文件夹树 / 目录 / 单文件，带磁盘选择器）**、分享链接（提取码 / 有效期 / 次数上限）、Range 流式下载、**中英双语界面（含后端错误文案）**

## 快速开始

```bash
# 1. 安装依赖（npm workspaces，一次装完前后端）
npm install

# 2. 建配置文件
copy server\.env.example server\.env      # Windows
# cp server/.env.example server/.env      # macOS / Linux

# 3. 初始化数据库（SQLite，自动生成 dev.db）
npm run db:push

# 4. 启动（后端 3000，前端 5173）
npm run dev
```

打开 `http://localhost:5173`，**第一个注册的账号自动成为管理员**；它一旦建立，登录页的注册入口就自动消失，之后只能由管理员开通账号。

也可以分开启动：

```bash
npm run dev:server
npm run dev:web
```

## 打包与部署

### 第一步：怎么打包

在**源码目录**（`ShareEverything/`，就是有 `package.json` 的那层）执行：

| 命令                     | 产出                                           | 适用场景                    |
| ---------------------- | -------------------------------------------- | ----------------------- |
| `npm run pack`         | `dist/` 目录                                   | 目标机器能联网，自己跑             |
| `npm run pack:zip`     | `dist/` + `release/*.zip`（约 2MB）             | 拷给别人，对方自己 `npm install` |
| `npm run pack:offline` | `dist/` + `release/*-offline-*.zip`（约 100MB） | **目标机器断网**，双击就能跑        |

产物结构：

```
dist/
  server/        后端编译后的 JS，入口 server/index.js
  public/        前端构建产物，由后端直接托管
  prisma/        schema.prisma（离线包还含预建好的 dev.db）
  package.json   生产依赖
  .env           首次打包自动生成（含随机 JWT_SECRET 与 ACCESS_CODE_KEY），重打包会保留
  VERSION        本次发布的版本号（语义版本+打包时刻，如 0.2.0+2026.10.17.2244）
  build-info.json  版本号 + 打包时间 + 打包模式 + Node 版本
  CHANGELOG.md   这一版改了什么（随包分发）
  LICENSE        Apache-2.0 许可全文
  start.bat / start.sh / 运行说明.md
  node/          离线包才有：自带 Node 运行时
  node_modules/  离线包才有：已装好的生产依赖 + Prisma 引擎
```

### 版本号：语义版本 + 打包时刻

版本号是**两段拼起来的**，形如 `0.2.0+2026.10.17.2244`：

- `+` 之前是**语义版本**，来自根 `package.json` 的 `version`，人工维护、每次对外发版递增，
  与 [`CHANGELOG.md`](CHANGELOG.md) 的一条记录一一对应 —— 回答「这是哪一版、改了什么」看的是它。
- `+` 之后是**打包时刻**（年.月.日.时分），只是 build metadata。同一版本改一行重打也能区分是哪个包，
  又不会把 `version` 炒成每次都不一样（那样依赖比对和升级判断就乱了）。

写进三处，三者始终一致：

| 位置                              | 形式                            | 给谁看                            |
| ------------------------------- | ----------------------------- | ------------------------------ |
| `dist/VERSION`                  | `0.2.0+2026.10.17.2244`       | 人和外部脚本，单行纯文本                   |
| `dist/build-info.json`          | 同上，另有 `appVersion` / `build` / 打包时间 / 模式 / Node 版本 | 程序读（要单独取某一段就拆字段，别 parse 字符串） |
| `dist/package.json` 的 `version` | `0.2.0`                       | npm 生态，只放语义版本                  |

压缩包名里用紧凑形式 `share-everything-offline-20261017-1435.zip`，其中的时刻与上面的号一一对应；
同一分钟内重复打包会自动补上秒，不会把刚打出来的包覆盖掉。

运行时想看当前跑的是哪个版本，三个地方都能看到：

- 界面**侧边栏左下角**、登录页底部
- 启动日志第二行：`版本: 0.2.0+2026.10.17.2244（2026-10-17 22:44:56 打包）`
- `GET /api/version`（公开，无需登录）；`GET /api/health` 里也带 `version` 字段
  （health 的诊断字段如 pid、存储路径**仅本机可见**，详见[接口表下方](#apihealth-为什么不返回路径和-pid)）

源码直接跑（`npm run dev`）时没有这些文件，版本显示为 **dev** —— 刻意区别于任何一次发布包，  
免得把本地开发误当成某个历史版本。

### 离线包（`npm run pack:offline`）

目标机器**什么都不用装、不用联网**：依赖、Prisma 引擎、Node 运行时、建好表的 SQLite 库全部在包里。  
多了三步：在包内 `npm install --omit=dev` → `prisma generate` + `db push` 预建库 → 拷贝 Node 运行时。

体积参考（0.2.0 实测）：目录 **289MB**，压缩包 **104MB**（`node.exe` 占 83MB，是压缩包的主体）。  
压缩这一步比较慢（几千个小文件 + 80MB 的 node.exe），视磁盘速度约 1~3 分钟；  
只要目录不要压缩包的话用 `npm run pack` 更快。

### 第二步：安装包的用法

把 `dist/` 整个目录（或解压后的 zip）拷到目标机器。

**离线包：直接双击 `start.bat`**（Linux / macOS 跑 `./start.sh`），没有其他步骤——  
不需要 `npm install`，也不需要 `npm run db:push`。启动脚本会优先使用包内自带的 Node。

**标准包：**

```bash
cd dist
npm install        # 装生产依赖（含 pm2），postinstall 会自动 prisma generate
npm run db:push    # 建表，生成 prisma/dev.db
```

之后每次**双击 `start.bat`** 就行，不用再敲命令。Linux / macOS 用 `./start.sh`。

首次启动后浏览器打开 `http://localhost:3000`：

- **第一个注册的账号自动成为管理员**；建好之后登录页的注册入口自动消失（没有开关可配，也不会有"点了才报错"的注册页）
- **管理员忘密码时的应急通道**：把 `.env` 里的 `ALLOW_ADMIN_RESET_PASSWORD` 改成 `true` 并重启，
  就能用管理员账号在登录页直接填一个新密码完成重设（旧密码不对时，本次填的密码会被设为新密码并登录）。
  **该通道只认服务器本机**（127.0.0.1 / localhost），所以要在服务器上打开 `http://127.0.0.1:3000` 操作；
  从别的机器访问时，即使开关开着也只会得到"账号或密码错误"。
  **用完记得改回 `false`** —— 开启期间本机的任何错密码都会被写成新密码
- 改端口：编辑 `.env` 里的 `PORT`，重启生效
- **服务在后台跑，关掉命令行窗口不影响它**（要停用 `stop.bat`）

**注意**：标准包要求目标机器装 **Node 20 或更高版本**（`node -v` 可查）；  
离线包不需要，Node 运行时已经在包里了。

**生产环境前后端共用一个端口**（默认 3000），不需要 Nginx 反代，也不再有跨域问题。  
后端按 `WEB_DIST` → `./public` → `../public` → `../web/dist` 的顺序探测前端产物目录，  
找到就托管，找不到就只当 API 服务跑（开发模式的行为）。  
未命中的 `/api/*` 一律返回 JSON 404，只有不带扩展名的路径才回退到 `index.html` 交给前端路由。

打包脚本自带 ZIP 写入器（store 模式，零外部依赖），不调用 `powershell` / `zip` / `tar`，  
三条命令在不同机器上是否可用、参数是否一致，都不影响打包结果。

## 进程守护与保活

服务由 **pm2** 托管。产物目录里那些脚本就是它的操作面板：

| 双击                                       | 作用                     |
| ---------------------------------------- | ---------------------- |
| `start.bat`                              | 启动（已在跑就跳过，不会起第二个）      |
| `status.bat`                             | 守护状态 + 探一次 HTTP 健康检查   |
| `logs.bat`                               | 实时跟随日志（Ctrl+C 退出）      |
| `restart.bat` / `stop.bat`               | 重启 / 停止                |
| `clean-logs.bat`                         | 清理 pm2 抓取的日志与超期日志后自动重启 |
| `autostart-on.bat` / `autostart-off.bat` | 注册 / 取消开机自启（需管理员权限）    |

命令行等价形式（Linux / macOS 通用）：

```bash
node tools/ctl.mjs start|stop|restart|status|logs|clean-logs|autostart on|off
```

**`.bat` 里没有逻辑**——它们只是"找 node → 调 `tools/ctl.mjs` → pause"三行。  
真正的实现在 `tools/` 下的三个 `.mjs` 里：可读、可改、能单独用 node 跑起来验证；  
`ecosystem.config.json` 由 `tools/setup.mjs` 在每次启动时按当前位置生成。

保活策略（在 `ecosystem.config.json` 里可调）：

| 项                           | 默认值         | 说明                           |
| --------------------------- | ----------- | ---------------------------- |
| `autorestart`               | 开           | 进程退出后 3 秒自动拉起                |
| `exp_backoff_restart_delay` | 200ms       | 反复崩溃时指数退避，不会把 CPU 和日志刷爆      |
| `max_restarts`              | 20          | 连续不稳定重启超过这个次数就停下来，不再无脑拉      |
| `max_memory_restart`        | 1G          | 内存超限自动重启，防止长时间运行越吃越多         |
| `kill_timeout`              | 8s          | 先走优雅退出（关 HTTP → 断数据库），超时才强杀  |
| `exec_mode`                 | fork / 1 实例 | SQLite 只允许一个写进程，绝不能用 cluster |

**单实例**：端口就是互斥量。已有实例在跑时，新进程会在 `listen` 阶段拿到 `EADDRINUSE`，  
打一条明确提示后以退出码 2 终止——不会出现两个进程抢同一个 SQLite。

**开机自启**默认是"登录后启动"而不是"开机即启"，这样进程拥有你自己的文件访问权限，  
磁盘发布挂载本机目录才不会因为权限问题读不到。想改成开机即启（无人登录也跑），  
把 `tools/ctl.mjs` 里 `schtasks` 的 `/sc onlogon` 换成 `/sc onstart /ru SYSTEM`，需要管理员权限。

**打包分发时不要把 `.pm2/` 和 `logs/` 一起带上**——那是运行期状态，`.gitignore` 已经排除。

### 日志

| 文件                                   | 说明                                        |
| ------------------------------------ | ----------------------------------------- |
| `logs/app-YYYY-MM-DD.log`            | **主日志**，按天滚动，保留最近 `LOG_KEEP_DAYS`（默认 14）天 |
| `logs/pm2-out.log` / `pm2-error.log` | pm2 抓的同一份控制台输出，内容与主日志重复                   |

主日志由应用自己写（`server/src/utils/logger.ts`），**跟着进程走而不是跟着守护方式走**：  
开发时 `npm run dev:server`、手工 `node server/index.js` 一样会落盘。  
实现上直接接管 `console`，所以进程里任何地方（包括框架内部）的输出都会进文件，不用逐处改造。

pm2 那两个文件被守护进程一直持有句柄，Windows 上**无法从外部截断或改名**（实测 `EPERM`），  
所以给了一条 `clean-logs.bat`：先停服释放句柄 → 删文件 + 按 `LOG_KEEP_DAYS` 裁主日志 → 自动重启。

> 顺带记两个试过不通的路：`max_size` / `retain` 是 **pm2-logrotate 模块**的参数、pm2 本体不认；  
> 把 `out_file` 指向 `NUL` 也不行——Windows 只把**裸文件名** `NUL` 当设备，pm2 传的是绝对路径，  
> 结果真在目录里创建了一个 8.7MB、名叫 `NUL` 的实体文件。

## 怎么用

1. **搭结构**：左侧「磁盘发布」→ 点「新建文件夹」搭出逻辑目录。这类文件夹只存在于页面上的分组，**不对应任何磁盘路径**
2. **发布内容**：先选中某个文件夹，再点「发布目录」或「发布文件」。名称自己填（留空会用所选项目末段自动填），**路径点「选择…」在弹窗里点选，不用手敲绝对路径**。原文件不移动、不复制，只是映射进来
3. **浏览与分享**：目录节点点「浏览」进目录，靠面包屑和「返回上级」上下穿梭；文件或目录都能点「分享」→ 可设提取码、有效期（小时）、下载次数上限。目录分享对方打开后是打包下载（ZIP）
4. **整理**：每项右侧「更多」里可以重命名、移动到别的逻辑文件夹。删掉逻辑文件夹会把它下面的子项一起从资源库移除，但**磁盘上的原文件一个都不会动**
5. **拿到链接**：「我的分享」里复制链接，形如 `http://<服务器IP>:5173/s/xxxxxx`
6. **对方访问**：其他电脑打开该链接，填提取码即可下载；链接直接走后端 3000 端口的接口
7. **管账号**：管理员点左侧「用户管理」可以**新增账号**（可指定角色与存储配额）、**重置他人密码**、**删除账号**；任何已登录用户在右上角用户名下拉里都能「**修改密码**」（需填原密码）。**密码一旦被改动，该账号在其它浏览器 / 设备上的登录状态会立刻失效**

文件库（上传区）用法相同，只是文件存在 `server/storage/users/<用户ID>/` 下，占用个人配额（默认 2GB）。

#### 配额是怎么算的

配额在**写盘之前**判定，而不是写完再回滚 —— 超了 413，磁盘上一个字节都不会多占。

三个口径，统一由 `server/src/utils/quota.ts` 提供，所有写盘入口都必须从那里取数：

| 口径 | 含义 | 用在哪 |
| --- | --- | --- |
| `stored` | 已落库文件的字节总和 | 空间用量显示 |
| `pending` | 在途上传任务**已落盘**的分片（在临时目录里，但确实占着磁盘） | 写盘判定 |
| `reserved` | 在途上传任务**声明**的总大小 | 建任务时判断还敢不敢接 |

于是有两个「剩余」：写盘用 `remaining = quota − stored − pending`，建任务用 `remainingReserved = quota − stored − reserved`。
用承诺量（`reserved`）而不是已收字节来接新任务，是因为一个声明 2GB 的任务只传了 10MB 时 `pending` 才 10MB，
按它放行等于超额承诺 —— 早期版本正是只统计已落库文件，导致**并发建 N 个上传任务就能绕过 N 倍配额**。

除了写盘前判定，写入**过程中**还有一道 `ByteLimitStream` 按剩余额度截断：客户端声明的大小可以撒谎，
只有边写边数才能真正保证磁盘占用不越线。它超限后会继续把剩余请求体读完（不再往盘上写），
这样客户端收到的是干净的 413，而不是连接被重置。

## 用户与账号管理

| 场景            | 入口                          | 需要什么                    |
| ------------- | --------------------------- | ----------------------- |
| 新增账号          | 「用户管理」→ 新增用户（仅管理员可见）        | 邮箱、用户名、初始密码；角色与配额可选     |
| 重置**别人**的密码   | 「用户管理」→ 某行「重置密码」（仅管理员）      | 新密码即可，**不需要原密码**；对方需用新密码重登 |
| 修改**自己**的密码   | 右上角用户名 → 修改密码               | 原密码 + 新密码               |
| 删除账号          | 「用户管理」→ 某行「删除」（仅管理员）        | 二次确认；不能删当前登录账号、不能删掉最后一个管理员 |

删除账号会级联清除它的文件库、分享链接与磁盘发布记录（数据库层面），**并顺带清掉磁盘上的个人文件目录**，不可恢复。

**改密即踢下线**：每次签发 JWT 时都会把一个令牌版本号（`User.tokenVersion`）写进载荷，鉴权时与库里的值比对，不相等就判定令牌已作废。因此只要有密码变动（管理员重置、本人修改、登录页找回），该账号此前签发的所有令牌立即失效，用户必须用新密码重新登录。这套机制没有会话表，代价只是每个带鉴权的请求多一次按主键查询。顺带地，鉴权时角色也**以数据库为准**，管理员被降权后手里的旧令牌当场失去管理员权能。

## 权限模型

| 区域                        | 谁能看                             | 谁能改                             |
| ------------------------- | ------------------------------- | ------------------------------- |
| **磁盘发布**（`Mount`）         | 按可见范围：所有人 / 仅发布者 / 指定用户（管理员一律可见） | 发布者本人 + 管理员可改名 / 移动 / 移除 / 改可见范围 |
| **我的文件**（`FileItem`，网页上传） | 仅本人                            | 仅本人                             |
| **分享链接**（`Share`）         | 拿到链接的人，无需登录 | 创建者本人            |
| **账号管理**（`User`）          | 仅管理员        | 仅管理员（新增 / 重置他人密码 / 删除）；本人可改自己的密码 |

资源库里的节点分三种，共用同一张表，所以可以任意嵌套成一棵逻辑树：

| 类型         | 对应磁盘         | 能做什么                |
| ---------- | ------------ | ------------------- |
| **逻辑文件夹**  | 无（纯分组）       | 装别的节点、重命名、移动、整棵移除   |
| **目录**     | 一个真实目录       | 浏览、逐文件下载、分享（打包 ZIP） |
| **文件**     | 一个真实文件       | 直接下载、分享             |

### 磁盘发布的可见范围

每个节点都能单独设可见范围，三档（默认 `PUBLIC`，与最早的「全站共享」行为一致）：

| 值            | 谁能看见                      |
| ------------ | ------------------------- |
| `PUBLIC`     | 所有登录用户（默认）                |
| `PRIVATE`    | 只有发布者本人                   |
| `PROTECTED`  | 发布者 + 授权名单里指定的用户          |

判定集中在 `server/src/utils/mountAccess.ts`，有两条规则容易搞错，这里写死：

1. **管理员一律可见**。与「改名 / 移动 / 移除限发布者或管理员」是同一套口径——否则别人设了私有的项一旦出问题，管理员既看不见也删不掉，只能去改数据库。
2. **父级收紧则整棵子树一并收紧**。判定沿祖先链取最严的一级，所以把文件夹设成 `PRIVATE` 就等于整条分支对外关闭，不会出现「以为关了、其实子项还是 `PUBLIC` 被看见」的情况。

看不见的时候，浏览、下载、就它建分享链接，一律回 **404「发布不存在」**——刻意与「本来就没这一项」返回完全一样，否则拿 id 遍历就能靠错误码差异把私有项的存在性探出来。

它与**分享出去的外链**是两条独立的通道：分享链接自带提取码，本来就是发布者主动开放的，不受可见范围约束；但反过来，对**看不见**的项不能开链接，否则私有就只是把列表入口藏起来了。

因此**发布权限默认是收窄的**（`MOUNT_CREATE_ROLE=ADMIN`），**可发布的路径范围也默认收窄**。相关配置：

```env
# ADMIN（默认）= 仅管理员可发布；USER = 任何登录用户都能发布
MOUNT_CREATE_ROLE=ADMIN

# 允许发布 / 允许在选择器里浏览的路径范围，分号（或竖线）分隔。
# 不配置时默认收窄到 <运行目录>/Download（打包后就是安装目录下的 Download，会自动创建）。
# 这一项同时管两件事：① 能发布哪些路径；② 「选择路径」弹窗能浏览到哪儿。
# 想恢复成「不限制」（能登录即可发布任意目录）：MOUNT_ALLOWED_ROOTS=*
MOUNT_ALLOWED_ROOTS=D:\share;D:\movie
```

⚠️ **想放行整块盘要写 `D:\`，不要写 `D:`**。Windows 下不带反斜杠的 `D:` 是「D 盘的**当前工作目录**」，
不是盘根：`path.resolve('D:')` 得到的是**服务进程的启动目录**。所以配成 `MOUNT_ALLOWED_ROOTS=D:`
时，白名单会变成安装目录本身 —— 选择器只能浏览到安装目录，再往上就是边界。
现在服务会把裸盘符自动纠正成 `D:\`，并在启动日志里打印生效范围（`磁盘发布范围: D:\`），
但配置里写全 `D:\` 最不会产生歧义。

### 硬盘不够用了，怎么平滑扩容

磁盘发布能看到的范围就是 `MOUNT_ALLOWED_ROOTS`。想接第二块盘，按推荐程度有三种做法：

**① 把新的物理位置直接加进白名单（推荐，零技巧、零风险）**

```env
MOUNT_ALLOWED_ROOTS=<安装目录>\Download;E:\media;F:\movie
```

选择器里会多出 `E:\media`、`F:\movie` 两个起始根，能力和 Download 完全一样。
不依赖任何 Windows 技巧，白名单语义也保持完好。

**② 把整个 Download 换成指向大容量磁盘的目录联接（junction）**——适合「一块盘用满了换一块」

```bat
:: 先把原 Download 的内容挪到新盘，再把 Download 本身变成指向它的链接
robocopy "<安装目录>\Download" "E:\se-download" /E /MOVE
mklink /J "<安装目录>\Download" "E:\se-download"
```

之后落进 Download 的文件实际都写在 E 盘，程序端**不需要改任何配置**。
`mklink /J` 建的是 NTFS 目录联接，**普通用户即可创建，不需要管理员权限、也不需要开开发者模式**
（`mklink /D` 符号链接才需要）。升级重打包时注意别把这个目录覆盖掉。

**③ 只把 Download 下的某个子目录指到别的盘**（如 `Download\movies` → `E:\movies`）

```bat
mklink /J "<安装目录>\Download\movies" "E:\movies"
```

⚠️ **这种做法在本项目里默认会被拦住，而且拦得对**：链接指向根之外的路径一律判为越界
（`isEscapeLink` / `isMountPathAllowed`），选择器里根本不显示这个入口，手敲路径也是 403。
这是刻意的安全设计，不是 bug。要用它必须把**链接的真实目标**也加进白名单：

```env
MOUNT_ALLOWED_ROOTS=<安装目录>\Download;E:\movies
```

（或者直接 `MOUNT_ALLOWED_ROOTS=*` 彻底不限制——只建议在完全互信的机器上用。）

**顺带：网页上传的文件（个人文件库）走的是另一条路**

它落在 `STORAGE_ROOT`（默认 `<运行目录>/storage`，开发时是 `server/storage`，打包后是安装目录下的 `storage`），
**完全不受上面的白名单约束**，所以扩容更省事——直接把 storage 搬到大盘即可：

```env
STORAGE_ROOT=E:\se-storage
```

或保持默认路径、改成链接（适合不想动配置的场合）：

```bat
robocopy "<安装目录>\storage" "E:\se-storage" /E /MOVE
mklink /J "<安装目录>\storage" "E:\se-storage"
```

> Windows 没有「把两个目录合并成一个视图」的原生能力——资源管理器里的「库」只是视图层，对程序无效，
> `subst` 只能把路径映射成盘符。真要**把多块物理盘合成一个卷**，得用「存储空间」（Storage Spaces）
> 或磁盘管理里的跨区卷；代价是一块盘损坏会波及整个卷，RAID 才是更稳的选择。

## 目录打包下载（ZIP）

分享的对象从「只能是文件」放宽到了「文件或目录」。目录分享的公开页会先做一次预检，  
再一次性打包成 ZIP 流式下载。

```
打开链接 → 预检（遍历统计，带限额）→ 流式 ZIP（边读边发）→ 浏览器直接落盘
```

| 阶段 | 接口                              | 说明                                       |
| -- | ------------------------------- | ---------------------------------------- |
| 预检 | `GET /api/s/:code/archive/plan` | 返回文件数、子目录数、总大小、压缩包大小；命中限额时返回 `truncated` |
| 打包 | `GET /api/s/:code/archive`      | 边遍历边生成 ZIP 字节流，不落临时文件、不在内存里攒整个包          |

**压缩档位**（公开页可切换，默认 `smart`）：

| 档位            | 行为                          | 进度显示         |
| ------------- | --------------------------- | ------------ |
| 极速 `store`    | 完全不压缩                       | 有精确总大小，显示百分比 |
| 智能 `smart`    | 影音 / 图片 / 已压缩包直存，其余 deflate | 无总大小，显示已下载字节 |
| 高压缩 `deflate` | 全部 deflate                  | 同上，明显更慢      |

ZIP 本身是零依赖生成的（`server/src/utils/zip.ts`）：deflate 用 Node 内置 `zlib`，  
其余字节自己拼。文件名带 UTF-8 flag（中文不乱码）、超过 4GB 或 65535 条目自动启用 ZIP64、  
文件条目统一用数据描述符（每个文件只读一遍磁盘，不在头上回填 CRC）。

**限额与保护**（`server/.env`）：

```env
ZIP_MAX_FILES=50000            # 文件数上限
ZIP_MAX_TOTAL_BYTES=21474836480 # 总大小上限（20GB）
ZIP_MAX_DEPTH=32               # 目录层级上限，同时兜住循环软链接
ZIP_CONCURRENCY=2              # 同时最多几个打包，其余排队
ZIP_THROTTLE_SECONDS=60        # 同一分享两次打包的最小间隔，防手抖
```

超出限额时预检会标记 `truncated`，打包请求直接 413 并说明是哪一项超了。  
客户端断开（关页面 / 取消下载）会立刻停止遍历并归还并发名额。

**不支持断点续传**：ZIP 是即时生成的，响应带 `Accept-Ranges: none`。  
大目录请看下面的后台打包任务。

打包时的安全规则与浏览一致：跳过指向发布目录外的软链接、用 realpath 去重防止软链接成环、跳过系统目录。

### 后台打包任务（大目录）

同步流式要求一条 HTTP 连接撑到打包结束，几十 GB 的目录风险太大。  
超过阈值（`ARCHIVE_ASYNC_THRESHOLD_BYTES` / `ARCHIVE_ASYNC_THRESHOLD_FILES`）  
就改成两步：先在服务端把 ZIP 生成好，再当普通文件下载——下载阶段因此支持 Range 断点续传。

```
POST /archive/jobs   →  202 + jobId（后台开始打包）
GET  /archive/jobs/:id      →  轮询进度（已处理 N/M 个文件）
GET  /archive/jobs/:id/file →  下载结果（普通文件，支持 Range 续传）
DELETE /archive/jobs/:id    →  取消并删除临时文件
```

预检结果里的 `suggestAsync` 会告诉前端该走哪条路，用户不需要自己判断。

- 同一个分享 + 同一种档位会**复用**已有任务：打包好的直接返回，正在打包的共享同一份进度
- 下载次数只在任务第一次被下载时计一次（续传会产生多个 Range 请求，按请求计数会把次数刷爆）
- 打包进度按条目上报，写库节流 500ms，不会因为上报进度拖慢打包
- 结果保留 `ARCHIVE_JOB_TTL_HOURS` 小时，过期由定时任务清理；启动时还会把上次残留的 RUNNING 任务重置为 FAILED
- 两种模式共用同一个 `createArchiveStream()`，区别只是 pipe 的目标是 HTTP 响应还是文件

## 分片上传与断点续传

大于 8MB 的文件自动走分片流程，小于 8MB 直接整传。

**分片大小和并发数不暴露成可填的数字**，而是由「上传策略」自动推导——因为这两个值是耦合的：

- 内存峰值 ≈ 并发数 × 分片大小，分开填很容易配出爆内存的组合
- 分片数 = 文件大小 ÷ 分片大小，而服务端合并是串行「读一片写一片」，分片太多会把 complete 拖成分钟级

推导规则（`web/src/utils/uploadPolicy.ts`）：

- **分片大小**：按目标分片数反推 → 取到 2 的幂 → 夹在档位上下限之间
- **并发上限**：`min(内存预算 ÷ 分片大小, 档位硬上限, 服务端 maxConcurrentChunks)`
- **实际并发**：从档位起点做慢启动，成功则 +1，失败（含服务端 429）则减半，同 TCP 的 AIMD

三档预设（前端可切换，存 localStorage）：

| 档位     | 目标分片数 | 分片范围      | 并发上限 | 适用     |
| ------ | ----- | --------- | ---- | ------ |
| 稳健     | 256   | 512KB–8MB | 2    | 弱网、跨公网 |
| 均衡（默认） | 128   | 1MB–16MB  | 4    | 多数场景   |
| 极速     | 64    | 4MB–32MB  | 8    | 千兆局域网  |

```
POST /api/uploads/init            建任务，秒传命中直接返回文件
POST /api/uploads/:id/chunk       传单个分片（multipart：index + file）
GET  /api/uploads/:id             查进度，返回已收到的分片序号
POST /api/uploads/:id/complete    合并分片并入库
DELETE /api/uploads/:id           取消，丢弃已收分片
```

前端行为和它对应的实现：

| 能力    | 实现方式                                         |
| ----- | -------------------------------------------- |
| 断点续传  | 服务端保留已收分片，`init` / 状态查询返回序号列表，前端只传缺失的        |
| 刷新后继续 | `localStorage` 记住 `uploadId`，重选同一文件时找回未完成的任务 |
| 秒传    | 前端用 Web Crypto 抽样（头/中/尾各 1MB）算指纹，命中已有文件直接完成  |
| 失败重试  | 分片失败自动退避重试，同时把并发减半；累计失败超 12 次才判定任务失败         |
| 并发自适应 | AIMD：成功攒够一批就加一路，失败或收到 429 就减半                |
| 暂停/继续 | 传输面板上的按钮，暂停只是停止发新分片，已上传部分保留在服务端              |


**下载侧**用 HTTP Range 按 4MB 一段拉取并流式写入磁盘：

- 支持 File System Access API 的浏览器（Chrome / Edge）走 `showSaveFilePicker`，直接边下边写，不占内存，可暂停 / 继续 / 取消
- 不支持的浏览器（Firefox / Safari）回退到浏览器原生下载，由浏览器自己利用服务端的 `Accept-Ranges` 续传
- 服务端 `streamFile()` 统一处理 `Range`，返回 206 与正确的 `Content-Range`

未完成的分片默认保留 3 天（`UPLOAD_TASK_TTL_DAYS`），之后自动清理。

## 界面语言（国际化）

界面支持**简体中文 / English** 两种语言，**前端文案与后端错误提示一起切**。切换入口在三处：

| 位置 | 说明 |
| -- | -- |
| 侧边栏左下角 | 登录后的常规入口（与版本号同一处） |
| 登录页底部 | 还没登录时也能切 |
| 分享公开页 | 拿到链接的人（无需登录）也能切 |

语言选择存在 `localStorage` 的 `se_locale`，**首次访问按浏览器语言自动判定**，之后跟着用户的选择走。
下拉里的选项永远显示「简体中文 / English」自身语言的写法——只看不懂当前语言的人也能找到切回去的入口。

### 后端文案为什么用中文当 key

后端文案表（`server/src/i18n/en.ts`）的 **key 就是中文原文**（gettext 风格的 msgid）。好处有两个：

- **抛出点一个字都不用改**：`throw new AppError('账号或密码错误', 401)` 保持原样，翻译只发生在响应层
- **漏译不会变成空白或 key 名**：查不到就**原样回退成中文**，最坏情况只是界面里夹一句中文，不会出现 `files.title` 这种东西

需要插值的文案在抛出处多带一个 `i18n` 参数（`message` 仍是插好值的中文，供日志看）：

```ts
throw new AppError(
  `同时上传的分片过多（上限 ${config.maxConcurrentChunks}）`, 429,
  { key: '同时上传的分片过多（上限 {}）', params: [config.maxConcurrentChunks] },
)
```

`{}` 按出现顺序替换。**打包任务的失败原因是个例外**：它写在数据库里（写的时候不知道将来谁会看），所以存中文，**在读出来响应时**才翻译。

### 语言从哪来：`X-Locale` 而不是 `Accept-Language`

优先读自定义头 **`X-Locale`**（`zh*` → 中文，`en*` → 英文），取不到才退回 `Accept-Language`。

不用 `Accept-Language` 作为首选，是因为它是浏览器的**禁止头**——JS 改不动它，它反映的是**操作系统语言**而不是用户在界面里选的语言。前端 axios 拦截器统一注入 `X-Locale`，所以界面切到英文后，后端返回的报错也是英文。用 curl 直接调接口时不带头，走 `Accept-Language` 或默认中文：

```bash
curl -X POST http://127.0.0.1:3000/api/auth/login \
  -H 'Content-Type: application/json' -H 'X-Locale: en-US' \
  -d '{"account":"x","password":"y"}'
# {"error":"Incorrect account or password"}
```

前端还有一处**不能只靠文案判断**的地方：分享公开页原本靠错误文案里有没有「过期」二字来识别 410（分享失效）。文案一换就会失灵，所以传输快照里加了 `errorStatus`，改成**看 HTTP 状态码**。

Element Plus 组件自己的文案（分页、日期、确认框按钮…）有独立的语言包，与 vue-i18n 是两套，通过 `ElConfigProvider` 手动同步（见 `web/src/i18n/index.ts` 的 `ELEMENT_LOCALES`）。

### 改文案后怎么自检

```bash
npm run check:i18n
```

`scripts/check-i18n.ts` 会查四件事，全绿才算过关：

1. 后端所有文案（`new AppError('…')` 与直接 `t(locale, '…')` 两处）都进了英文表
2. 前端代码里用到的每个 `t('…')` 键，中英两份词典里都有
3. 两份词典**结构一致**（一边有一边没有＝漏译）、没有**没人引用的废弃词条**
4. 界面代码里**没有残留的硬编码中文**（词典目录除外）

运行时拼接的键（`t(\`${key}.title\`)`、`policyKey()`）脚本看不到字面量，靠脚本顶部的 `DYNAMIC_KEY_PREFIXES` 白名单放行——**加新的拼接点时要同步那里**。
个别行本来就不该翻译（语言下拉的语言名）在行尾写 `// i18n-ignore` 豁免。

配套命令：`npm run typecheck`（前后端类型检查）。

### 写界面时要注意的两件事

**① 宽度按英文留。** 同样的意思，英文通常比中文长 1.5–2 倍（`上传策略：均衡` → `Upload mode: Balanced`）。
表格列宽、按钮区宽度、下拉框宽度都按**较长的一方（英文）**定，中文下多出的空白无害；
反过来按中文定，英文就会换行、截断，甚至把按钮挤出可视区（`el-table` 会整表横向溢出，末列直接看不见）。

**② 日期别直接 `toLocaleString()`。** 它不带参数时跟的是浏览器/操作系统的语言，
会出现「界面切成英文、日期仍是中文格式」。统一走 `formatDateTime()`（`web/src/utils/format.ts`），它显式传入当前界面语言。
字节大小的 `humanSize()` 用 `KB/MB/GB`，两种语言一致，不需要处理。

#### `/api/health` 为什么不返回路径和 pid

健康检查是**公开接口**，任何人都能访问。它早期会把 `pid`、启动时间、存储根目录、日志路径一起返回，
等于对外公布服务器的目录布局、进程号与运行时长（后者能推断重启和补丁周期）。现在做了分级：

- **普通请求**（含所有外部来源）：只回 `{ ok, version, time }`
- **来自本机的请求**：额外附上 `pid` / `startedAt` / `uptimeSec` / `node` / `storageRoot` / `logFile` / `webDist`

本机判定复用 `utils/request.ts` 的 **fail-closed** 实现：只看 TCP 对端地址是否为回环，
**请求里带任何转发头（`X-Forwarded-For` / `X-Real-IP` / `Forwarded`）就一律不算本机**。
所以在 nginx 反向代理部署下，所有请求的 TCP 来源都是 `127.0.0.1`，本机能识别的只剩「连代理也假装不了」
这一条 —— 该部署会稳定地只给最小集合，不会「悄悄放行所有人」。要在那种部署下看诊断信息，直接在服务器上 `curl 127.0.0.1:3000/api/health`。

`/api/version` 同理，只放「这个包是什么」，运行时状态已收进 health 且仅本机可见。两个接口都带 `Cache-Control: no-store`。

所有接口都认 `X-Locale` 请求头（`zh*` / `en*`），决定**报错信息**用哪种语言返回；不带头时看 `Accept-Language`，都没有则中文。详见[界面语言](#界面语言国际化)。

## 安全设计

- **目录穿越防护**：所有用户传入路径都经 `safeJoin()` 校验，解析后必须仍在根目录内，否则 403
- **软链接防护**：`resolveInside()` 会 `realpath` 展开链接后再校验一次——指向挂载点内部的链接正常访问原始文件，指向外部的（symlink / Windows junction）一律 403，浏览时也不列出
- **发布目录互斥**：新增目录发布时会检查与已有目录是否存在包含关系，避免同一批文件在资源库里出现两次
- **选择器范围收敛**：磁盘选择弹窗只能浏览 `MOUNT_ALLOWED_ROOTS` 之内的路径，且**每一次列举请求都重新校验**——顺着软链接跳到范围外会被当场拒绝；只对有权发布的用户开放
- **逻辑树不可越界**：移动节点时会拒绝「移到自己或自己的子孙下」，防止把树拧成一个环
- **上传隔离**：分片临时目录的 `uploadId` 只取自数据库记录，不直接用请求参数拼路径；非本人任务一律返回 404
- **分片参数服务端兜底**：前端给的分片大小会被夹到 `[MIN_CHUNK_SIZE, MAX_CHUNK_SIZE]`，分片数超过 `MAX_CHUNKS_PER_TASK` 时自动放大分片；同一用户并发分片数超过 `MAX_CONCURRENT_CHUNKS` 返回 429。前端不可信，服务端必须自己挡住内存峰值
- **越权校验**：上传文件与分享严格比对 `userId`；磁盘发布的读权限按可见范围判定（`PUBLIC` 全站 / `PRIVATE` 仅发布者 / `PROTECTED` 授权名单，管理员豁免、父级收紧则子树一并收紧），看不见时一律回 404 而非 403，不泄露存在性；改名 / 移动 / 移除 / 改可见范围限发布者本人或管理员，发布动作受 `MOUNT_CREATE_ROLE` 控制
- **密码**：bcrypt 加盐哈希，不存明文
- **改密即踢下线**：JWT 载荷里带 `tokenVersion`，鉴权时与库里的值比对，不相等即 401（见「用户与账号管理」一节）。改密、重置、删除账号都会作废该账号此前签发的全部令牌；鉴权时 `role` 也以数据库为准，降权立即生效
- **账号管理边界**：用户管理接口全部挂在 `adminGuard` 下；删除账号时禁止删自己、禁止删掉最后一个管理员，且「检查 + 删除」在同一事务内，防止并发把管理员删空；新建账号的唯一性校验同样放在事务里
- **密码找回限本机**：`ALLOW_ADMIN_RESET_PASSWORD=true` 时，重设密码只接受来自回环地址（127.0.0.1 / ::1）的请求，非本机一律按普通密码错误回绝；判定只看 TCP 对端地址、不看任何请求头，**且只要请求带了 `X-Forwarded-For` / `X-Real-IP` / `Forwarded` 就一律不算本机**——所以伪造转发头和「前面挂了反向代理」两种情况都会 fail-closed（拒绝），不会误放行
- **分享**：提取码、过期时间、下载次数三重限制，可随时删除失效；目录打包预检同样要求提取码，避免分享链接变成目录探测器。提取码**加密入库**（见下），创建者在「我的分享」里可以随时看到原文、复制、重设
- **打包限额**：`ZIP_MAX_FILES` / `ZIP_MAX_TOTAL_BYTES` / `ZIP_MAX_DEPTH` 三重上限，超出直接 413；并发数与单分享节流防止反复点击把 CPU 和磁盘打满
- **JWT 密钥不会退回硬编码值**：优先用 `.env` 里的 `JWT_SECRET`；没配、或者还是模板里的占位值（`please-change-this-secret` / `dev-secret-please-change`）时，读 `<运行目录>/.jwt-secret`，没有就随机生成 48 字节写进去（权限 0600，已进 `.gitignore`），启动时会打印提示。所以**任何情况下都不会用一个人人皆知的密钥**——那个值一旦公开，任何人都能签出管理员令牌。打包脚本首次生成 `.env` 时也会写入随机密钥，重打包会保留
- **CORS 默认关闭**：前后端同源（开发靠 Vite 代理、生产共用一个端口）根本不需要跨域，所以**默认不注册 CORS 插件**，接口只接受同源请求。只有显式配置 `CORS_ORIGINS` 白名单才启用，且是精确匹配；写 `*` 时强制放弃携带凭证（浏览器不允许两者并存）。原来「反射任意来源 + 允许携带凭证」的写法已彻底移除
- **请求体限额分两层**：全局 `BODY_LIMIT` 默认 **1MB**，只约束 JSON 这类会被 Fastify **整个缓冲进内存**的请求体；multipart 的上传路由单独放宽到 `MAX_UPLOAD_SIZE`，并另有逐请求的分片大小限制。既堵掉「一个巨大的 JSON 打出内存尖峰」，又不会误伤大文件上传
- **限流**：全局 `RATE_LIMIT_MAX`（默认 1200/分）；**登录与注册**压到 `RATE_LIMIT_LOGIN_MAX`（默认 **10 次 / 5 分钟**）——这是全项目唯一靠猜就能拿到权限的入口；整目录打包这类高开销公开接口单独限额（`RATE_LIMIT_ARCHIVE_MAX`）。限流**不启用 `trustProxy`**，`req.ip` 取的就是 TCP 源地址，与上面「本机判定」保持同一套 fail-closed 口径。超限统一回 429 + `Retry-After`，文案跟着界面语言走
  - **例外是刻意留的**：分片上传与可续传下载这两类路径**显式关掉了**按请求数限流。一次上传天然是成百上千个分片请求；一次下载是按 4MB 一段顺序发 Range，1GB 的文件就是 256 个请求，在千兆局域网下一分钟就超过任何合理的阈值——按请求数限流只会先打到正常用户头上。它们的边界交给别的手段：分片大小与在途并发上限、单文件大小上限、下载次数上限
- **提取码在库里是密文，且能反复回显**：提取码需要能随时回来看（发出去之后过几天还得再抄一次），所以**不能只存哈希**。落库前用 AES-256-GCM 加密，格式是自描述的 `v1:<盐>:<iv>:<认证标签>:<密文>`（全 base64url）：
  - **每条记录独立随机盐**（16 字节），再加 HKDF-SHA256 派生该条记录专用的数据密钥。同一个提取码在库里得到完全不同的密文，彩虹表失效，一条记录被攻破也不牵连其他记录
  - 密钥链两层：`.env` 里的 **`ACCESS_CODE_KEY`**（可以填一句 ≥8 字符的口令，启动时先过 scrypt 拉高爆破成本，进程内只算一次）→ 主密钥 → 每条记录的盐 → 记录密钥。盐在**加密前**就参与派生，而不是拼接在密文后面
  - GCM 的认证标签保证完整性：密文被改一个字节，解密直接失败，不会得到一段"看起来合法"的垃圾，因此不需要额外挂 HMAC
  - 明文**只在两个地方出现**：创建/重设的那一瞬间，以及创建者自己读「我的分享」时由服务端解密后返回。公开接口（`GET /api/s/:code`）只回 `needAccessCode`，`accessCode` 恒为 `null`；其他用户也拿不到
  - 密钥换了怎么办：库里旧码解不开时，列表里会标 `accessCodeBroken`，校验接口回 500 并明确说「无法解密」，用 `PATCH /api/shares/:id` 重设即可恢复（分享本身不受影响）。所以 **`ACCESS_CODE_KEY` 必须与 `.env` 一起备份，且不要和 `dev.db` 放在同一份备份里**——两者分开保管，单独泄露任何一份都无效
  - 升级前写入的明文提取码：读取端按有无 `v1:` 前缀兼容，第一次被**正确**校验通过后顺手加密回库（懒迁移，不需要停机跑脚本）
  - 另外补上了长度约束：**4–64 位、拒绝控制字符**，创建时自动 trim。老代码是 `body.accessCode || null`，能设成 `"1"`——库泄露后这种码不用爆破，看一眼就出来了
- **提取码防爆破**：按 `IP|分享code` 统计**失败**次数（校验成功即清零），默认连续错 8 次后拒绝 10 分钟（`ACCESS_CODE_MAX_FAILS` / `ACCESS_CODE_WINDOW_SECONDS`）。之所以不直接用路由级限流：正常浏览一次分享要发好几个请求（预检、建打包任务、轮询进度、Range 下载），按请求数限流会先把正常用户挡在门外，而真正要防的只是「同一个人对着一个分享反复猜」。提取码比对走 `crypto.timingSafeEqual` 定长比较，不会因为「前几位猜对了」而暴露时序差异
- **安全响应头**：`@fastify/helmet` 统一加上 CSP、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer` 等。CSP **没有沿用默认策略**，而是按本项目实际形态逐条写死（见下）
- **文件与目录名统一校验**：`POST /api/files/mkdir`、`POST /api/files/upload`、`POST /api/uploads/init` 三处入口共用 `utils/fs.ts` 的 `assertSafeName()`。目录穿越本身由 `safeJoin` 挡着，但名称还会被拼成 `relPath` 存进数据库，之后所有查找、下载、删除都按它来 —— 所以这里收紧到「真能在磁盘上原样存在的单段名称」：路径分隔符、`< > : " | ? *` 等非法字符与控制字符、系统保留名（`NUL` / `CON` / `COM1`…，含 `NUL.txt` 这种带扩展名的写法）、首尾空格与尾点（Windows 会**悄悄裁掉**再落盘，Linux 不会，两边就会对不上）、超过 255 字节，一律拒绝。**是报错而不是静默改写**：把用户输入的空格悄悄 trim 掉，建的就和界面显示的不是一个名字了，更难排查。`mkdir` 还改成只递归建**父目录**、目标严格建一层——早先 `recursive: true` 配上带分隔符的名字会一口气建出多级，而数据库只登记最后一层，中间几层成了看不见也删不掉的孤儿目录；同名文件则回 409

### 安全响应头（helmet）

本项目是 Vite 构建的单页应用，产物只有一个外链 module 脚本 + 一个外链 CSS，页面里没有内联脚本、没有内联事件处理器、没有 `eval`、没有 Web Worker、没有 blob URL——所以 CSP 可以收得很紧：

```
default-src 'self'; base-uri 'self'; object-src 'none';
script-src 'self'; script-src-attr 'none';
style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self' data:;
connect-src 'self'; form-action 'self'; frame-ancestors 'none'
```

三处**刻意**的取舍，改之前先看清楚：

1. **`style-src` 必须留 `'unsafe-inline'`**。它同时兜住 CSP3 的 `style-src-attr`，而 Vue 的 `:style`、Element Plus 的定位样式写的都是元素的 style **属性**。去掉不是「稍微丑一点」，是布局直接散架。
2. **关掉了 HSTS**（helmet 默认开启，max-age 半年）。浏览器一旦收到就会记住「这个主机必须走 HTTPS」，之后用 `http://` 访问会被自动升级成 `https://`——而服务端只有 HTTP，等于站点直接打不开，且在 max-age 到期前很难撤销。**等真正上了 HTTPS 再打开**。
3. **CSP 里没有 `upgrade-insecure-requests`**，道理同上：纯 HTTP 部署下它会让页面里所有请求被升级成 HTTPS 从而全部失败。

另外 `frameguard: deny`、`referrerPolicy: no-referrer`、`crossOriginResourcePolicy: same-origin` 都保持开启；`crossOriginEmbedderPolicy` 关闭（它是为 `SharedArrayBuffer` 这类特性准备的，本项目用不上，开着反而给引入任何跨源资源埋雷）。

上线前必须做的：

1. `JWT_SECRET` 想轮换或打算多实例部署时，在 `.env` 里显式配一个随机长串；不配也能安全运行——应用会自动生成并落盘到 `.jwt-secret`，**不会退回到固定密钥**
2. **`ACCESS_CODE_KEY` 与 `.env` 一起备份，但不要和 `dev.db` 放同一份备份**。丢了它，已有的提取码全部解不开（分享还在，重设即可）；它和数据库一起泄露，加密就白做了
2. **上 HTTPS**（目前下载链接把 token 放在 URL query 里，明文传输有泄露风险；且抽样指纹依赖 `crypto.subtle`，只在 localhost 或 HTTPS 下可用，否则自动跳过秒传）。**上完 HTTPS 记得把 helmet 的 HSTS 打开**，并把 CSP 的 `upgrade-insecure-requests` 加回去——这两个按当前 HTTP 部署是刻意关掉的
3. 确认 `ALLOW_ADMIN_RESET_PASSWORD=false`（只在管理员忘密码时临时打开，用完立刻关；该通道仅限服务器本机，代码里写死，不受配置影响）
4. **用低权限账号启动服务**（Node 进程的权限就是磁盘发布能读到的边界）
5. **`server/storage` 与 `dev.db` 定期备份**
6. 如果把前端部署到了别的域名，才需要配 `CORS_ORIGINS`；同源部署**保持不配**就是最严的状态
